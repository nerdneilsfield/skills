# 当前上下文

- 当前分支: !`git branch --show-current`
- 近期提交主题（用于识别惯例）: !`git log --format=%s -30`
- 变更状态（含未跟踪文件）: !`git status --short`
- 已跟踪文件变更: !`git diff HEAD`
- 当前暂存区变更: !`git diff --cached`

如果上面的命令没有展开，先自行运行这些命令再继续。

# 任务

根据上方状态与 diff，将所有未提交的变更按逻辑分组并逐次提交。提交信息必须先匹配仓库惯例，再决定是否使用 Conventional Commits；不得为了格式统一而改写仓库既有风格。

用户调用本 Skill，即表示授权分析当前工作区并执行所需的本地 commit。先展示简短提交计划；若分组、变更归属、暂存范围和提交格式均可从上下文可靠判断，则在同一轮立即逐组提交，不询问「是否继续」或等待确认。该授权不含修改业务内容、丢弃变更、push、创建 PR、merge、rebase 或改写历史。

仅在存在会实质改变提交内容或历史结构、且无法从仓库与对话判断的抉择时暂停，例如：

- 未跟踪或已暂存内容的归属不明，可能把用户无关工作纳入提交；
- 同一文件的 hunks 属于不同任务，却无法安全分离；
- 两种分组方式具有不同回滚含义，且没有明显较安全的选择；
- 用户明确只要分析、提交计划或 commit message，未要求实际提交。

提交数量、普通 scope 命名、单笔或多笔等可按下文规则可靠决定者，不算需要用户抉择。历史格式混杂时使用既定 fallback，不为此停下。

如果提供了 `$ARGUMENTS`，将其作为模块、格式或摘要提示；明确指定优先，不要默认把它当作 scope。

## 先判提交风格

提交计划前，查看当前仓库最近约 20–30 条提交，并优先查看与本次变更同模块的最近提交。按以下顺序选择格式：

1. `$ARGUMENTS` 或项目规范明确指定格式时，遵循它。
2. Conventional 提交在近期历史中明显占多数，且同模块也使用时，使用 Conventional。
3. 其他格式（例如 `<scope>: <summary>`、`<area> <summary>`）在近期历史中占多数时，照抄其结构、语言、大小写和标点。
4. 历史混杂或样本不足时，以同模块最近提交为准；仍无法判断时，使用 Conventional 作为 fallback，并在计划中标明。

同一仓库可因模块而有不同惯例，但不得凭目录名臆造 scope。提交主题保持简短。

若同一文件含多个独立逻辑单元，仅在能安全区分时用 `git add -p` 拆分；否则保持文件完整，避免制造难以回滚的半个配置。

## 第一步：分析并制定提交计划

先输出一个提交计划，格式如下（`<subject>` 使用上一步判定的风格）：

```
📋 提交计划（共 N 次；风格：<判定结果>）：

1. <subject>
   涉及文件: <file-a>, <file-b>
   分组理由: <同一逻辑变更>

2. <subject>
   涉及文件: <file-c>
   分组理由: <独立逻辑变更>

暂存策略: <文件级或具体 hunks>
```

计划只展示仓库内相对路径；不要展示仓库绝对路径、远端 URL 或历史 commit hash。展示是执行前的透明记录，不是默认审批关卡。除非命中上方真实抉择或用户明确只要分析/计划，否则输出计划后立即执行第二步。

## 第二步：逐次执行提交

按计划顺序，对每一组：

1. 重新检查状态，确认没有把后续组或用户原有暂存变更带入本组。
2. 用 `git add -- <具体文件路径>` 只暂存该组；同文件拆分时用 `git add -p`。禁止 `git add -A`、`git add .`、`git commit -am`。
3. 检查 `git diff --cached --check`，再确认暂存区文件和 hunks 只属于本组。
4. 执行 `git commit -m "..."`；提交信息使用已判定的仓库风格。
5. 报告该次提交结果，再进行下一组。

已有多个不相关文件处于暂存区时，不要擅自清空或 reset。本组是整文件时优先用 `git commit --only -- <本组路径>`；若 hunks 重叠导致无法安全隔离，停止并说明需要用户整理暂存区。

任一 commit 失败（含 hook、冲突或身份配置问题）即停止，不使用 `--no-verify` 绕过；保留现场并报告原因。

## 拆分原则

- 按用户意图、依赖关系和审查/回滚边界分组；不同模块通常分开，同一功能涉及实现、测试、文档时可合并。
- 同一模块的多份配置若共同完成一次 rollout，保持一个提交；互不相关的配置变更才分开。
- 能安全按 hunks 分离时再拆同一文件；无法安全分离时保持一个提交并在计划中说明。
- 变更确实只有一个逻辑单元时，直接单次提交，不为凑次数拆分。

## 提交信息

使用仓库已选定的格式。仅当判定为 Conventional 时，使用：

```
<type>(<scope>): <简短描述>

[正文：说明改了什么、为什么]

[Footer：Closes #123、BREAKING CHANGE 等]
```

按仓库历史选择语言和大小写；不要为非 Conventional 提交强行套用这些 type。

使用时直接输入 `/co-commit`。Skill 先给出分组计划与风格判断；无真实抉择时随即逐组提交，完成后报告 commit 与剩余工作区状态。

## Gotchas

- `git diff HEAD` 不含未跟踪文件，必须单独阅读并纳入分析。
- `git commit --only -- <路径>` 提交这些路径的工作区全文，不是已暂存的 hunks。同文件按 hunk 拆分时不能用它，否则未计划的 hunks 会一并进入提交。
- `git add -p` 需要交互输入。shell 不支持交互时，把本组 hunks 写成补丁，用 `git apply --cached` 暂存。
- 不因文件扩展名、测试、文档或注释身份自动拆分；只有独立意图才拆分。
- 提交主题不强制 50 字符、祈使句、首字母大写或句末无标点，除非仓库历史如此。
