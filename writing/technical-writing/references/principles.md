# Core principles

## Priority order

发生冲突时，按以下顺序取舍：

1. 技术正确性与安全性。
2. 准确、明确、完整、一致。
3. 读者能否完成任务、作出判断或快速查到事实。
4. 项目既有术语、接口名称和文档约定。
5. 一般风格偏好。

不要为符合风格规则而改动技术含义。项目或产品已有经过审定的安全术语、法定文本、接口拼写或 UI 标签时，以其为准。

## Write for reader intent

先确定读者此刻要做什么：学习、完成目标、理解机制、查询事实、定位故障、实现接口、操作设备或验证结果。内容围绕该意图组织，不按开发者实现过程流水记账。

Bad:

> 我们先实现了缓存层，随后增加了命令行参数。

Good:

> 使用 `--cache-dir` 指定缓存目录。未指定时，工具使用 `$XDG_CACHE_HOME/acme`。

只保留会影响读者决策、操作或理解的内部实现信息。设计规范和原理说明本就面向实现时，内部结构才是主要内容。

## Make technical claims usable

技术陈述至少回答相关问题中的必要部分：谁或什么执行动作、在什么条件下、对什么对象、产生什么结果、受什么限制。

Bad:

> 超时后会自动处理。

Good:

> 若服务器在 30 s 内未返回响应，客户端取消请求，并返回 `ETIMEDOUT`。

不得省略会改变结果的参数、单位、范围、默认值、版本、权限、环境、时序或依赖。不要用“适当”“相关”“必要时”等词代替条件。

## Separate facts from assumptions

- 已验证事实：直接陈述，并保持与权威接口、代码、原理图、数据手册或测试结果一致。
- 合理推断：明确写成推断及其依据。
- 未知内容：标注待确认项；不要补齐看似合理的数值、错误码、寄存器位或安全要求。
- 建议：说明这是建议，不伪装成产品行为或强制要求。

## Keep examples truthful

示例是技术内容，不是装饰。

- 示例使用正文中存在的名称、参数、版本和约束。
- 命令应能复制执行；占位符必须说明替换方式。
- 输入、输出和错误示例应符合所述行为。
- 示例若省略内容，用不会改变理解的明确省略标记，并说明省略了什么。
- 修改正文后，同步检查示例、表格、图注和交叉引用。

## Prefer the smallest sufficient structure

标题、列表、表格和 callout 用于表达结构，不用于装饰。短文不必套完整模板；复杂文档也不要把多个读者意图压进连续散文。

- 有先后依赖：编号步骤。
- 无先后依赖：项目列表。
- 多个对象共享固定属性：表格或一致的小节。
- 一个对象需要解释多个字段：description list、参数表或字段表。
- 只有一句必要信息：直接写一句，不造新章节。

## Common anti-patterns

- **实现日志当用户文档**：改写为用户目标、条件、动作和结果。
- **同义词轮换**：一个概念固定一个术语；重复优于歧义。
- **标题复述正文**：标题说明任务或主题，正文直接进入有效信息。
- **层层总结**：删除“总体而言”“综上所述”等无新增信息的段落。
- **营销化承诺**：用可验证事实替代“强大”“无缝”“轻松”“显著提升”。
- **假精确**：没有来源的数值、等级、时间和兼容性不得写成确定事实。
- **格式代替含义**：粗体、颜色或 Note 不能补救缺失的条件、风险或动作。
