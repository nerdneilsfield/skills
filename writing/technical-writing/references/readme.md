# README writing

README 是仓库的门面，常是读者唯一会看的一页；用对待代码的标准对待它。README 不是文档本体，而是通往其余信息的入口：让读者快速判断、给出最短成功路径、链接到一切相关内容。有完整文档站的项目，README 应收缩为 elevator pitch 加链接集；没有文档站的项目，README 可组合 overview、quick start、configuration 和少量 reference，但仍以入口为主，不倾倒全部内容。

## Four-question test

扫一眼 README 的读者应能快速回答四个问题：

1. 这能解决我的问题吗？
2. 我能用这个代码吗？（许可证、平台、运行时版本要求、项目状态）
3. 谁做的？
4. 去哪里了解更多？（文档、CI、发布、社区）

写作和 review 都用这四问检查：答案能否被快速找到。第 2 问通常由一句话定位、徽章和 GitHub 仓库侧栏的 License 信息回答，第 1 问由定位与 Highlights 回答，第 3、4 问由 Overview 和链接区回答。若环境允许，亲自按 quick start 走一遍并记录每个卡住的点；请不了解项目的人试读是给人而非 agent 的建议。

## Default structure

按项目类型调整节序，小节可增删，但四问对应的信息不可缺：

1. 标题与一句话定位：它是什么、给谁用、一个差异点。这句话同时可作为 GitHub About description。
2. 可选的徽章行，紧跟定位，规则见 Writing rules。
3. Highlights：项目的主要卖点，逐条写成可验证的事实陈述，不用营销词；条数由事实决定。
4. Hook：截图、GIF 或极短代码示例，展示软件真实运行。这是无标题的媒体块，紧跟前屏内容，是快速浏览的读者最先看到的部分。
5. Overview：一两段说明问题、如何解决、不是什么；说明谁做的、项目状态（实验性、维护中或已停止维护）、在更大生态中的位置，可与其他方案作尊重性的简短比较。
6. Installation：目标包管理器的一行安装命令，加最低要求（运行时版本、平台）。开发或源码构建说明放文末或 `CONTRIBUTING.md`，不要混在这里吓跑普通用户。
7. Quick start：按 Installation 安装后，在全新环境复制即可跑通的最短路径；以源码克隆运行的独立应用才以干净 clone 为前提。结尾写明应观察到的结果（打开的 URL、输出片段或生成的文件）。
8. Usage：最常见的几个任务，每个配短示例和真实输出；其余内容链接到完整文档。
9. Configuration：只列高频项，默认值取自配置加载代码而非注释；链接完整配置参考。
10. Documentation and next steps：完整文档、how-to、issue tracker、讨论区、问答标签。
11. Contributing：如何反馈问题、提出需求、贡献代码或文档（翻译也是贡献）；链接 `CONTRIBUTING.md`。
12. License：SPDX 许可证表达式，链接到实际的许可证文件，多许可证项目逐一链接。

可选的 Development 节只放在最后：开发者环境搭建、测试、构建命令。

## Writing rules

- 先读仓库再写：名称、版本、入口、命令、配置项、许可证来自 manifest、配置加载代码、脚本和 `LICENSE`，不凭记忆。每条计划发布的事实应有来源，或标注待确认后省略。
- Quick start 的每条命令在全新环境实际执行一遍；无法执行时逐条追溯到实现（脚本、入口、构建文件），并向用户说明哪些只做了追溯。
- 徽章只放真实、可验证的信号：CI 状态、包版本、许可证、覆盖率（确有跟踪时）。数量以回答四问为限，至多约 6 个。优先使用读取真实来源的动态徽章，不手写版本号或许可证文字；只给已按该名称发布的包加 registry 徽章，CI 徽章只对应默认分支上确实存在的 workflow。
- 链接与图片：仓库内文档链接与图片使用相对路径；外链与徽章使用绝对 URL。README 会随包发布到 PyPI、npm 等包仓库时，展示性图片与站外可见链接改用指向 tag 或 commit 的绝对 URL，因为包仓库页面不解析相对路径，也不支持自定义 HTML 锚点。每张图片必须有 `alt` 文本。
- 代码块内不放 `$`、`#` prompt（会破坏复制按钮）；占位符用 `<angle-brackets>` 并在上一行说明替换方式。
- 语言跟随仓库既有公开文档语言；未被要求时不翻译已有 README。
- 语气友好、平实、面向平均水平读者；不用 hype 词（“强大”“无缝”“革命性”“blazing”），用可验证事实或机制说明代替，见 [principles.md](principles.md) 的营销化承诺规则。
- 标题默认使用纯文本。沿用仓库已有的 emoji 标题惯例时，注意 GitHub 生成锚点会删除大多数 emoji 符号，但保留文本中实际存在的 U+FE0F（URL 中编码为 `%EF%B8%8F`），emoji 后的空格在 emoji 被删除后会变成前导连字符，如 `## 🚀 Launch` 的锚点是 `#-launch` 而非 `#launch`。具体锚点以渲染结果或 slug 工具核对为准，不要凭源码肉眼判断；跳转目标需要稳定时使用显式 HTML 锚点。
- 静态图示使用实体底色或在深浅主题下均可读的配色，避免透明底深色文字的示意图在 GitHub 深色模式下不可见；GIF 等演示素材控制文件体积，不把大媒体直接提交进仓库历史。
- GitHub 会自动生成页面大纲，短 README 不必手写目录；长 README 如需目录，其中的锚点必须按上一条渲染核对。
- 修改功能时同步更新 README 对应段落；更新 README 时刷新而非追加，删除不再描述现状的状态和里程碑文字，不要在新章节下保留旧内容。

## Common failure

- 把 README 当完整文档或 API reference 倾倒，读者无法快速扫描，老用户也难以查找。
- 开头讲项目历史、目录树或内部架构，而不是解决什么问题。
- 安装部分混入 `git clone`、构建、子模块等开发说明，把普通用户挡在门外。
- 功能清单式罗列，没有说明每项解决什么问题、适用于谁。
- 手写版本号或许可证文字的静态徽章与实际情况漂移；徽章指向未发布的包、已改名的包或不存在的 workflow。
- 遗漏代码已暴露的用户可见能力、命令和硬限制；README 最常见的不准确是漏掉既有事实，而非修饰夸大。
- 手写程序输出示例导致与真实输出漂移；应从程序实际输出粘贴。
- 把过期的路线图和状态段落挪到新章节下堆积，新旧内容互相矛盾。
- 透明底示意图在深色模式下不可见；大体积 GIF 直接提交进仓库。

## Review checklist

- 读者能快速找到四问的答案；一句话定位同时适用于 About description。
- 每条 quick start 命令已在全新环境运行（包分发）或干净 clone（源码运行的应用）验证，或已追溯到实现并向用户说明。
- 每条功能列表项对应代码、文档或用户原话；无 hype 词。
- 运行时版本来自 manifest；配置默认值来自加载代码。
- 徽章至多约 6 个且均为真实信号；动态徽章的来源可达；LICENSE 徽章有对应的 `LICENSE` 文件。
- 仓库内相对链接、图片路径、锚点全部可解析；随包发布的 README 中图片与外链使用绝对 URL。
- 图片在深浅主题下均可读，且均有 `alt` 文本。
- License 段为 SPDX 许可证表达式，链接到实际许可证文件，并与 manifest 的 license 字段一致。
- 无过期状态段落；过期内容已删除而非移动到其他位置。
- 事实性声明经未参与起草的审阅者复核。
