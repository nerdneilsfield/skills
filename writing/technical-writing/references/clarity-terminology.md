# Clarity and terminology

## Name actor and action

句子应让读者知道谁做什么。优先使用具体主体和精确动词。

Bad:

> 配置完成后进行验证。

Good:

> 保存配置后，运行 `acme verify` 验证连接。

当 actor 不重要、未知，或技术对象本身是主题时，被动语态可以更清楚：

> 校准系数存储在只读寄存器 `CAL_OFFSET` 中。

不要为追求主动语态而虚构 actor，或反复使用“系统将会”“用户需要”。

## Put conditions before actions

条件、位置、权限和适用范围应出现在相关动作之前。读者不应执行到句末才发现动作不适用。

Bad:

> 运行 `flash --erase`，如果设备处于维护模式。

Good:

> 如果设备处于维护模式，运行 `flash --erase`。

多个条件会产生不同结果时，分别写出分支；不要把条件藏在括号、脚注或段尾。

## Make sequence explicit

有顺序要求时使用编号步骤及顺序词。`before`、`after`、`until`、`while`、`then` 应有明确参照对象。

Bad:

> 断开电源并拔下信号线。

Good:

> 1. 断开设备电源。
> 2. 等待状态指示灯熄灭。
> 3. 拔下信号线。

若动作可并行或顺序无关，勿伪造时序。

## Control sentence complexity

一句只承载一个主要判断。出现以下情形时拆句或改成列表：

- 两个以上 actor；
- 多组条件与例外；
- 连续三个以上动作；
- 多个 `and`、`or`、`以及`、`并且`；
- 修饰语离被修饰对象过远；
- 代词可能指向多个对象。

短句不是目的。若拆句会切断因果或造成重复，保留一个结构清楚的复句。

## One concept, one term

建立并维护当前文档内的术语映射：首选术语、允许缩写、禁止同义词、大小写和是否翻译。

- 同一对象不要在“节点”“主机”“机器”“实例”之间轮换。
- 接口、UI、数据手册或协议已命名的对象，沿用权威拼写。
- 新术语首次出现时定义；之后使用同一形式。
- 缩写只在能降低阅读成本时引入。首次出现通常写全称和缩写；行业内更常见的缩写可直接使用。
- 不要为了避免重复而把技术名词换成模糊代词，如“它”“该项”“相关内容”。

## Choose precise verbs

用能说明状态变化的动词替代空泛结构。

| Weak | Better |
| --- | --- |
| 进行配置 | 配置 |
| 进行删除操作 | 删除 |
| 实现日志的输出 | 输出日志 |
| 完成连接的建立 | 建立连接 |
| 对数据进行校验 | 校验数据 |

这些词并非一律禁用：

- “实现”可表示满足接口或算法契约：`Driver` 类实现 `Transport` 接口。
- “完成”可表示明确完成态：升级完成后，设备自动重启。
- “对应”可表示可验证映射：引脚 3 对应信号 `SDA`。
- “相关”仅在集合确实由上下文定义时使用；否则列出对象。
- “适当”“必要时”必须能由读者判断。给出触发条件、范围或责任角色。

## Preserve meaningful repetition

重复稳定术语、条件或安全动作，常比省略更可靠。可以删除无信息重复，但不得依赖读者从远处章节推断当前步骤的关键条件。

Bad:

> 对其进行处理，然后检查它的状态。

Good:

> 重启控制器，然后检查控制器的 `READY` 状态位。
